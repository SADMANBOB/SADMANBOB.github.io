# JavaScript bundle: measurement and architecture decision

Measured on the production build of `codex/production-hardening`, mobile
Lighthouse profile, median of three runs.

## Current size

| | Inspector | Contractor |
| --- | --- | --- |
| Raw | 362.8 KB | 334.1 KB |
| Gzip | 106.2 KB | 96.2 KB |
| Brotli | 90.1 KB | 82.1 KB |

GitHub Pages negotiates Brotli, so ~90 KB / ~82 KB is what a real visitor
downloads.

## Where the bytes come from

Attributed by walking the production sourcemap and grouping generated bytes by
originating module.

| Group | Inspector | Contractor |
| --- | --- | --- |
| `react-dom` | 49.8% | 53.7% |
| App shell (`App.jsx`) | 14.5% | 13.5% |
| Route content | 14.8% | 4.0% |
| `shared/` registries | 8.7% | 10.7% |
| Forms | 3.9% | 9.2% |
| `lucide-react` icons | 2.5% | 1.1% |
| `react` | 2.2% | 2.4% |
| Search dialog | 1.8% | 2.0% |
| `scheduler` | 1.0% | 1.1% |

## What this rules out

Two of the optimisations that would normally be first are already done:

- **Icons already tree-shake.** Every icon is a named import and `lucide-react`
  accounts for only 1.1–2.5% of the bundle. Rewriting to deep paths would
  change 8 files to save well under 1 KB.
- **Search is already lazy.** `SiteSearchDialog` dynamically imports the
  Pagefind runtime (`await import(bundlePath)`), so the search engine is not in
  the main bundle. Only the ~2% dialog shell is, and extracting that behind a
  Suspense boundary risks the dialog's focus management for roughly 2 KB.

## The measurement that governs the decision

JavaScript is **not** the current bottleneck:

- Total Blocking Time is 0–70 ms across all nine audited routes. The mobile
  gate is set at 250 ms.
- Main-thread work is not flagged on any route.
- The constraint on every route is Largest Contentful Paint (2.3–3.2 s), driven
  by render-blocking CSS and font delivery. The service chooser — measured at
  `/property-services/` in that baseline and now mounted at `/` — has **no
  JavaScript at all** and was the worst performer in the baseline at 0.79.

Cutting JavaScript would therefore not move the metric that is actually
limiting these pages. That is why no architectural change was made in this pass.

## Options

### 1. Keep current React hydration

- **Savings:** none.
- **Cost:** none. **Risk:** none.
- Leaves ~90 KB Brotli on every route, roughly half of it `react-dom`.

### 2. Route-level code splitting

- **Savings:** 15–25% of app code on narrow routes; nothing off `react-dom`,
  which is over half the bundle. Realistically 8–15 KB Brotli.
- **Cost:** moderate. Prerender plus hydration means each route's chunk must
  resolve before hydration completes, adding a request to the critical path.
- **Risk:** medium. Introduces a hydration waterfall on the very routes it
  slims, and can regress TBT even while cutting bytes.
- **Accessibility:** low risk. **Tests:** visual baselines unchanged; needs new
  hydration tests per route.
- **Verdict:** not justified while TBT is 0–70 ms. Revisit only if app code
  grows well past `react-dom`.

### 3. Preact compatibility alias

- **Savings:** the largest available — roughly 35–40 KB Brotli, since
  `react-dom` is ~50% of the bundle.
- **Cost:** low to apply, high to qualify.
- **Risk:** **high.** This project runs React 19 with `renderToString` SSR and
  `hydrateRoot`. Preact's compat layer tracks React's public API, not React 19
  internals, and any hydration mismatch would surface as silently broken
  interactivity on a lead-capture form.
- **Tests:** the entire cross-browser and visual suite would need re-approval.
- **Verdict:** do not adopt to chase a bundle number. Only worth exploring
  behind a full hydration and form-submission test pass on a dedicated branch.

### 4. Static pages with interactive islands

- **Savings:** the largest realistic ceiling — most routes ship near-zero JS,
  since the pages are already fully prerendered. Interactive surfaces are only
  the nav toggle, search dialog, disclosure groups and the two forms.
- **Cost:** high. This is a rewrite of the app shell and the hydration entry.
- **Risk:** medium-high, concentrated in the forms and the eligibility gate.
- **Verdict:** the right long-term shape for this site, but it is a dedicated
  project, not a step in a hardening pass. Explicitly out of scope here.

### 5. Removing client-side routing

- **Savings:** moderate; removes the router and lets each prerendered page stand
  alone. Pairs naturally with option 4.
- **Risk:** changes navigation feel and would need the scroll and focus
  behaviour on route change reimplemented as ordinary document navigation.
- **Verdict:** not justified. The task's own bar is a *measured* performance
  problem, and there is none: TBT is near zero and navigation is not flagged.

## Recommendation

**Stay on option 1 for now.** Ship the font, image and asset work already in
this branch, which addresses the metric that is actually limiting the pages, and
re-measure.

The next JavaScript work should only begin when one of these is true:

1. Mobile TBT exceeds ~150 ms on a real route, or
2. App code grows past `react-dom`'s share, making option 2 worthwhile, or
3. The owner wants the 0.95 mobile performance floor, in which case option 4 is
   the honest route and should be scoped as its own project.

The single largest remaining byte saving on this site is not JavaScript at all:
pinning Newsreader's optical-size axis would cut ~106 KB, more than any bundle
option except Preact. That is an owner typography decision, recorded in
`contractor-site-prototype/public/assets/fonts/FONT_SOURCES.md`.

## Applied in this pass

`vite` and `@vitejs/plugin-react` were listed as runtime `dependencies` in both
site packages. They are build tools and are now `devDependencies`. This does not
change the browser bundle; it corrects the dependency contract and shrinks any
production-only install. Both CI workflows use a plain `npm ci`, which still
installs dev dependencies, so the build is unaffected.
